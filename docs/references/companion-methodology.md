# 伴读页生成方法论

这份文档恢复自早期较完整的 Reading Companion 说明。它不是可安装的 skill 入口，而是给 `skills/reading-companion*/SKILL.md` 和开发者参考的丰富方法论。

当前约定：

- 可发布/可复制给 Claude Code 的 skill 入口统一放在 `skills/`。
- 本文件放在 `docs/references/`，只作为页面生成参考。
- 实际文件结构以 ReadPilot 当前 `data/books/<book-slug>/` 为准。

## 核心目标

将一本书转化为一个随读者阅读节奏自然生长的交互式 HTML 伴读系统。它不是一次性批量生成的课程，而是读者在阅读过程中不断提出问题，AI 只在需要时生成下一页。

## 目标读者

ReadPilot 面向主动求知者，而不是只想快速消费摘要的人。伴读页应帮助读者：

- 先看见书籍骨架，再进入细节。
- 与作者达成共识，理解作者如何使用核心术语。
- 提取核心论点、叙事线索、人物关系或概念框架。
- 批判性思考作者的盲点、时代局限和论证漏洞。
- 把书中的方法、判断或审美经验迁移到现实问题中。

因此，伴读页不是“拆书稿”，也不是把聊天回答搬进 HTML。它应该像一个可以复访的学习节点：聚焦、可互动、可检查，并能接回后续阅读。

## 核心原则

### 一次一页

每次用户明确请求生成页面时，只生成一个聚焦页面。

- “为第 2 章生成伴读页” -> 生成一个章节伴读页。
- “把时间碎片这个概念做成一个深挖页” -> 生成一个 deep-dive 页面。
- “生成一个比较 X 和 Y 的主题页” -> 生成一个 theme 页面。
- “把目前读到的内容做成阶段综合页” -> 生成一个 synthesis 页面。

不要一次批量生成全书课程。普通解释、摘要、检测题和轻量问答应留在 ChatPanel。

### 读者驱动

系统不预设完整阅读路线。读者决定节奏和方向：

- 读完哪个章节，就围绕哪个章节推进。
- 不理解哪个概念，就围绕那个概念生成深挖页。
- 想比较哪些人物、观点或主题，就生成对应主题页。

### 掌握学习

页面底部可以包含掌握检测区。读者回到 ChatPanel 讨论答案后，再决定下一步：

| 掌握度 | 判断依据 | 下一步 |
| --- | --- | --- |
| 完全掌握 | 能准确解释并迁移应用 | 推荐继续阅读或探索新主题 |
| 基本掌握 | 大方向正确，有小偏差 | 简短纠正后继续 |
| 部分理解 | 概念混淆或解释不稳定 | 生成 deep-dive 页面 |
| 尚未理解 | 回答错误或不知道如何开始 | 从更基础角度重建 |

### 主动阅读

伴读页要帮助读者主动阅读，而不是替读者消费内容：

- 原文引用要短且精确，不复制大段版权文本。
- 解释要把作者语言、读者语言和现实应用连接起来。
- 页面优先使用结构、图示、对照、检测和互动，不写成长篇讲义。
- 每个页面围绕一个清晰问题展开。
- 每屏只承担一个概念或一个推理步骤。
- 先用读者熟悉的比喻建立直觉，再回到作者文本和现实应用。

## 触发边界

伴读页生成必须由用户明确触发。以下请求应默认只在 ChatPanel 中回答：

- “帮我理解这一章”
- “总结这一节”
- “这个概念是什么意思？”
- “给我几道题”
- “我读完第 X 章了”

以下请求可以进入伴读页生成工作流：

- “为第 X 章生成一个伴读页”
- “把这个概念做成一个深挖页”
- “创建一个比较 X 和 Y 的主题页”
- “把目前进度做成阶段综合页”
- “更新 Hub / progress.json”
- “把这一节做成交互式 HTML 页面”

这个边界很重要：ReadPilot 的默认体验应该是轻量对话，只有用户需要可复访产物时才写入 `pages/` 和 `progress.json`。

## ReadPilot 文件结构

每本书的目录位于：

```text
data/books/<book-slug>/
  source.epub
  source.jsonl
  source-manifest.json
  progress.json
  companion/
    book-profile.md
    chapter-index.md
    topic-index.md
  pages/
    *.html
```

生成页面前，应先读取：

1. `progress.json`
2. 相关 `companion/*.md`
3. 目标章节或相关 chunks

不要为了生成一个页面重新处理全书，除非用户明确要求重建全书画像。

## 用户旅程

### 首次导入

1. 用户在书库导入 EPUB。
2. ReadPilot 将 EPUB 转换为 `source.jsonl` 和 `source-manifest.json`。
3. 应用创建或更新 `progress.json`。
4. 用户进入单本书 Hub，查看章节、笔记、进度和已生成页面。
5. 用户从 Hub 进入章节阅读页，在右侧 ChatPanel 提问。

首次导入不等于自动生成完整课程。除非用户明确要求，系统只准备数据和阅读入口。

### 持续伴读

每次用户明确要求生成页面时：

1. 读取 `progress.json` 了解当前状态。
2. 判断页面类型。
3. 读取相关 companion 索引和必要的 source chunks。
4. 生成一个自包含 HTML 页面。
5. 在 `progress.json.pages` 中登记页面。
6. 必要时更新 `currentFocus`、`themes`、`glossary`、`nextRecommendation`。
7. 在回复中说明生成了什么，以及下一步读什么或讨论什么。

### 掌握检测后的自适应

如果页面包含检测题，读者可以回到 ChatPanel 讨论答案。AI 根据回答质量更新掌握度：

| 掌握度 | 判断依据 | 下一步行动 |
| --- | --- | --- |
| 85-100 | 准确回答，能举一反三 | 推荐继续阅读或探索新主题 |
| 60-84 | 大部分正确，有小偏差 | 简短纠正后继续 |
| 30-59 | 概念混淆或解释不稳定 | 生成 deep-dive 页面 |
| 0-29 | 回答错误或不知道如何开始 | 从更基础角度重建 |

## 页面类型

### Hub / 书籍大本营

Hub 是单本书的阅读仪表盘。ReadPilot 当前应用内 Hub 由 React 渲染，参考模板见 [hub-template.md](hub-template.md)。

核心信息：

- 书籍标题、作者、开始日期
- 章节进度
- 已生成伴读材料
- 主题与术语
- 阅读时间线
- 下一步建议

### Overview / 全书透视

适合在读者想要看清全书结构时生成。

可以包含：

- 全书结构地图
- 核心人物、概念或论证框架
- 作者背景与写作动机
- 阅读路线建议
- 少量检视阅读级别问题

小说更关注叙事结构、人物关系和时间线；非虚构更关注论证结构、概念索引和方法论。

### Chapter / 章节伴读

围绕当前章节生成。

可以包含：

- 本章核心问题
- 章节结构拆解
- 短原文引用与白话解释
- 关键词提示
- 1 个合适的交互元素，如对照、流程、拖拽匹配、情境题或群聊式观点碰撞
- 1-5 个掌握检测题，数量随页面复杂度调整
- 一个清晰的“回到 ChatPanel 讨论”的提示

### Deep Dive / 深挖页

当读者对某个概念不理解，或检测中表现出混淆时生成。

要求：

- 不复制原章节页。
- 用新的比喻、新的角度或更基础的脚手架解释。
- 连接读者已经理解的概念。
- 检测题少而准，验证关键误区是否解除。

### Theme / 主题页

适合跨章节追踪一个主题、人物、概念或论证线索。

可以包含：

- 主题在不同章节中的变化
- 并排对比
- 作者如何逐步深化主题
- 与现实或其他书籍的连接
- 批判性问题

### Synthesis / 综合页

适合阶段性总结。

可以包含：

- 到目前为止的核心论点
- 知识连接图
- “只能记住三件事”的提炼
- 接下来章节的阅读预告
- 可迁移到现实场景的检测题

## 内容理念

### 视觉化优先

一本书已经是文字密度很高的媒介，伴读页不应再制造另一堵文字墙。

- 列表可以转成概念卡片。
- 论证可以转成流程图。
- 冲突观点可以做成左右视觉对比。
- 时间线、人物关系和主题演变应尽量图示化。

### 原文与解释分离

如果使用原文引用，左侧保留短引文，右侧做解释。不要篡改原文，也不要复制大段版权内容。解释部分可以使用大白话，但必须忠实于作者的实际意思。

### 测验测应用

检测题不要考年份、人名、边角信息。更适合考：

- 如何应用作者框架。
- 哪个例子违背作者逻辑。
- 某个论证的下一步是什么。
- 哪个选项“部分正确但不够精确”。

高质量干扰项应该来自常见误解，而不是明显荒谬的答案。

### 小说与非虚构的适配

| 维度 | 小说 | 非虚构 |
| --- | --- | --- |
| 透视页重点 | 叙事结构、人物关系、时间线 | 论证结构、概念索引、方法论 |
| 章节页重点 | 人物弧线、象征隐喻、叙事技巧 | 核心论点、论据链、思维转变 |
| 测验方向 | 文学分析、主题解读、人物动机 | 概念应用、逻辑推理、现实映射 |
| 批判角度 | 叙事选择、视角局限、文化偏见 | 逻辑漏洞、论据不足、时代局限 |

## 生成规范

### HTML 规范

- 页面应自包含，尽量只依赖字体等轻量外部资源。
- 使用 [design-system.md](design-system.md) 中的设计令牌。
- 使用 [interactive-elements.md](interactive-elements.md) 中的交互模式。
- 兼顾桌面、平板和手机。
- 原著引用块必须自动换行，不允许横向滚动。

### 导航规范

页面顶部应提供稳定导航：

- 返回 Hub 或上一层阅读页。
- 当前页面标题。
- 页面类型标签。
- 轻量进度或位置提示。

### 每页一个核心问题

一个伴读页解决一个明确阅读问题。标题、结构、检测题都围绕这个问题展开。

## 设计参考

生成 HTML 页面时优先参考：

- [design.md](design.md)
- [design-system.md](design-system.md)
- [interactive-elements.md](interactive-elements.md)
- [progress-schema.md](progress-schema.md)

页面应保持温暖阅读色调、稳定布局和清晰层级。不要为了炫技而加入过重动效。

## 常见避坑

1. 不要把普通问答都做成页面。
2. 不要一次批量生成多个页面。
3. 不要跳过 `progress.json`，每次写入前都要读取当前状态。
4. 不要生成页面后忘记登记到 `progress.json.pages`。
5. 不要复制大段版权原文。
6. 不要让 tooltip 或弹层被容器裁切。
7. 不要考察边角记忆，应考察理解和迁移。
8. 不要在 deep-dive 页面复制原页面内容，要换一个角度解释。
9. 不要让页面动效、装饰或卡片密度压过阅读本身。
10. 生成文件时始终以 `data/books/<book-slug>/` 为准。

## 更新规则

生成新页面后：

1. 在 `pages/` 写入 HTML。
2. 在 `progress.json.pages` 中登记页面。
3. 设置 `relatedChapters`。
4. 根据需要更新 `currentFocus`、`themes`、`glossary` 和 `nextRecommendation`。
5. 向用户说明生成了什么、改了哪些文件、下一步应该怎么读。

页面记录应符合 [progress-schema.md](progress-schema.md)。运行时 schema 以 [../../src/lib/schemas/progress-schema.ts](../../src/lib/schemas/progress-schema.ts) 为准。
